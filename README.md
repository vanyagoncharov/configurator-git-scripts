# Git вместо хранилища в обычном Конфигураторе — скрипты к статье

[![Статья на Инфостарте](https://infostart.ru/bitrix/templates/sandbox_empty/assets/tpl/abo/img/logo.svg)](https://infostart.ru/1c/articles/2823713/)

Скрипты к статье на Инфостарте
**[«Git вместо хранилища в обычном Конфигураторе: ветки задач, синхронизация базы и загрузка по git diff»](https://infostart.ru/1c/articles/2823713/)**.

В статье описан процесс, в котором разработчики остаются в обычном Конфигураторе, а git возит конфигурацию между
их базами. Здесь — две его части в виде скриптов PowerShell:

| Скрипт | Что делает |
|---|---|
| [`Import-GitDiff.ps1`](scripts/Import-GitDiff.ps1) | грузит в файловую базу только то, что изменилось между двумя коммитами, и обновляет конфигурацию БД |
| [`Lock-Infobase.ps1`](scripts/Lock-Infobase.ps1) / [`Unlock-Infobase.ps1`](scripts/Unlock-Infobase.ps1) | закрывает вход в серверную базу перед загрузкой и возвращает всё как было |

Без зависимостей: Windows PowerShell 5.1 (есть в любой Windows) или PowerShell 7, git, платформа 8.3.27+
(частичная загрузка `ibcmd` появилась в ней) или 8.5.

## Загрузка разницы: `Import-GitDiff.ps1`

Какой коммит сейчас в базе, вы указываете сами (`-From`). Скрипт берёт `git diff` между ним и текущим состоянием
ветки и решает, как грузить:

1. изменился `Configuration.xml` (состав или свойства конфигурации) — **полная**: частичная загрузка корня всё равно
   перечитывает всё дерево;
2. изменились `ParentConfigurations` (настройки поддержки) — **полная**;
3. есть удалённые файлы — **полная**: частичная загрузка объекты не удаляет;
4. файлов больше порога (300) — **полная**: так быстрее;
5. иначе — **частичная**, только изменённые файлы: `ibcmd config import files --partial`.

```powershell
# что будет загружено — без загрузки
.\scripts\Import-GitDiff.ps1 -Repo D:\repo -DbPath D:\bases\dev -From 3f9c2a11 -WhatIf

# загрузить
.\scripts\Import-GitDiff.ps1 -Repo D:\repo -DbPath D:\bases\dev -From 3f9c2a11
```

```

  Документ.ЭтапыПроизводства: модуль объекта
→ Частичная загрузка
```

Только файловые базы: `ibcmd config import` в серверную базу на 8.3.27 завершается «успешно», но оставляет
«Нарушена целостность структуры конфигурации» (возвращает её `ibcmd config reset`). Если платформа стоит
не в `Program Files\1cv8`, задайте `ONEC_ROOT` (например, `E:\Programs\1C\1cv8`) или передайте `-Ibcmd`.

## Серверная база: `Lock-Infobase.ps1` и `Unlock-Infobase.ps1`

```powershell
.\scripts\Lock-Infobase.ps1 -Infobase test_erp -PermissionCode 4321 -InfobaseUser Админ -InfobasePassword ***
try {
    # загрузка Конфигуратором с /UC 4321
} finally {
    .\scripts\Unlock-Infobase.ps1 -Infobase test_erp -InfobaseUser Админ -InfobasePassword ***
}
```

Через `rac` и сервер администрирования кластера (`ras`, по умолчанию `localhost:1545`):

1. **Кто в базе?** Есть сеансы — скрипт показывает их и ничего не меняет.
2. **Прежние значения блокировки сначала пишутся в файл**, потом вход и регламентные задания запрещаются с кодом
   разрешения. Если машина упадёт посреди загрузки, `Unlock-Infobase.ps1` вернёт блокировку по этому файлу.
3. **Ещё раз: кто в базе?** Кто-то мог войти между шагами 1 и 2 — тогда блокировка возвращается как была.
4. Загрузка Конфигуратором с `/UC <код>`.
5. **Вернуть как было** — и при ошибке тоже.

```
1. Проверка сеансов: в базе никого нет
2. Прежние значения сохранены: ...\infobase-locks\test_erp.json
   Вход и регламентные задания запрещены.
3. Повторная проверка: в базе никого нет
...
Блокировка возвращена: вход разрешён, регламентные задания разрешены.
```

## Грабли, на которые стоит рассчитывать

- **Объекты на замке поставщика по одному не загружаются**: «редактирование объекта метаданных … запрещено».
  Правки типовых объектов — только полной загрузкой или после снятия с замка.
- **8.5 и «Unknown exception».** На 8.5.1 частичная загрузка изредка падает на исправном наборе файлов,
  а повтор проходит.
- **`ConfigDumpInfo.xml` в git не храните**: он у каждой базы свой.
- **Память.** `ibcmd` на ERP занимает до 5,5 ГБ; при ~1 ГБ свободной памяти загрузка идёт в 5–9 раз дольше.

## Проверка

```powershell
powershell -File tests\Run-Tests.ps1
```

Без платформы: план загрузки, перевод путей в объекты метаданных, изменения между коммитами на временном
git-репозитории. Загрузка проверялась на файловой базе 8.3.27 (конфигурация с БСП, 5 392 файла), блокировка —
на локальном кластере 8.3.27.

## Свой движок выгрузки

Самое долгое в этом процессе — сама платформа: чтобы превратить CF поставщика в XML, `ibcmd` создаёт временную
базу, загружает в неё CF и выгружает. На ERP это больше десяти минут. Я пишу собственный разбор внутреннего
формата, который выдаёт тот же XML, что и платформа, байт в байт. Что уже работает и где он будет применяться —
[docs/engine.md](docs/engine.md).

## Чего здесь нет

Скрипты — две детали процесса из статьи, а не сам процесс. Остальное собрано в Windows-приложении
**[Konflow](https://konflow.ru)**:

- база сама помнит загруженный коммит, и правки никогда не выгружаются «не в ту» ветку;
- задачи-ветки со статусами, переключение между задачами, тестовые сборки и релизы с CF, CFU и описанием;
- конфликты между задачами видны до слияния;
- серверные базы и базы с хранилищем — Конфигуратором, с проверкой сеансов и запретом входа;
- расширения, резервные копии, откат выпущенной задачи.

Замеры на УНФ, УТ и ERP: на ERP переключение задачи занимает 2–3 минуты против 10 с половиной на полную
загрузку — [konflow.ru/benchmark-typical](https://konflow.ru/benchmark-typical).
